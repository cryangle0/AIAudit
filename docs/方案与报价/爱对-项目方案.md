## 第一章 项目背景与建设目标

### 1.1 业务背景

童装电商业务在多个自媒体/电商平台开店（抖音、淘宝/天猫、拼多多、快手、视频号小店、微信小店、小红书等），同时拓展海外市场（俄罗斯 OZON、Wildberries、英国 TikTok Shop、美国 Amazon）。每月财务团队需要将**平台账单**、**聚水潭 ERP 销售数据**、**自维护商品成本**三方数据交叉核对，定位差异并核算各店铺/商品真实利润。

### 1.2 当前痛点

**痛点一：人工对账效率低**。每个平台账单字段格式不一致，财务需要打开多个 Excel 手工比对订单号、销售收入、聚水潭实发金额、聚水潭实发成本，每月需要 3-5 天才能完成对账。

**痛点二：差异定位难**。订单可能出现金额翻倍（聚水潭多行登记）、聚水潭缺失、平台缺失、利润异常等多种异常，没有统一规则无法批量识别。

**痛点三：成本数据孤岛**。商品成本（标费/辅料/商品成本）散落在各部门 Excel，调整后历史报表无法保持稳定，没有审计追溯。

**痛点四：海外多币种**。OZON 用卢布、TikTok UK 用英镑、Amazon US 用美元，需要按月汇率换算到人民币统一核算，目前完全靠人工。

**痛点五：分配规则不透明**。推广费、运费险、红包、补贴等公共费用如何分摊到具体订单/商品，没有可配置的标准，每次都靠经验估算。

### 1.3 建设目标

构建一套**纯前端可独立运行**的多平台财务自动对账系统，覆盖商品资料维护、跨平台账单导入、聚水潭对账、汇率换算、费用归集与三层分配、利润核算、报表生成全链路。在满足客户《系统初稿模板》和《财务自动对账系统-需求表》全部 20 项需求的同时，做到：

- **零后端依赖**：浏览器端解析 Excel + localStorage 持久化，开箱即用
- **跨平台统一**：11 个平台适配器统一映射到标准列名，对账引擎一套通吃
- **规则可配置**：分配标准用户可自定义，覆盖所有费用类型
- **审计可追溯**：成本变更全程记录操作人/时间/前后值
- **报表对齐 Excel**：账单汇总/账单明细/店铺利润/商品利润 4 张表表头与客户模板逐字一致

### 1.4 项目范围

| 范围 | 说明 |
|---|---|
| 系统类型 | 单页应用（SPA），React 19 + Vite 8 |
| 部署方式 | 静态托管，支持 GitHub Pages、内部服务器、私有 OSS |
| 数据存储 | 浏览器 localStorage（生产可对接后端 API） |
| 用户规模 | 财务/运营 5-20 人单点使用 |
| 浏览器要求 | Chrome 100+ / Edge 100+ |

## 第二章 功能架构与业务流程

### 2.1 功能模块全景

系统按"业务核算闭环"组织为 **6 大模块、19 个功能页**：

```
商品管理（3）           利润核算中心（4）        数据中心（7）
├ 商品资料              ├ 数据归集               ├ 应收汇总表
├ 商品成本              ├ 分配标准               ├ 应收明细表
└ 成本修改记录          ├ 数据分配               ├ 账单汇总表
                        └ 利润分析表             ├ 账单明细表
汇率管理（1）                                    ├ 店铺利润表
└ 汇率维护              店铺管理（1）            ├ 差异分析表
                        └ 店铺/平台配置          └ 商品利润表
系统设置（3）
├ 角色管理
├ 权限管理
└ 数据备份
```

### 2.2 核心业务流程

#### 2.2.1 月度对账主流程

```
1. 财务进入「差异分析表」页
2. 选择平台（如抖音）+ 月份（如 2026-01）
3. 上传平台资金账单 Excel + 聚水潭导出 Excel
4. 点击「开始对账」
5. 系统自动执行：
   a. 平台适配器把原始列映射到标准列名
   b. 聚水潭按订单号聚合 实发金额/实发成本/销售毛利
   c. 对账引擎按订单匹配，分类到 5 个差异桶
6. 生成 KPI 卡片 + 差异明细表 + 月度公共扣费列表
7. 点击差异行可下钻查看原始流水
```

#### 2.2.2 商品成本变更流程

```
1. 财务进入「商品成本」页
2. 编辑某 SKU 的标费/辅料/商品成本
3. 系统自动写入「成本修改记录」（操作人/时间/前后值）
4. 后续对账使用新成本，已生成的报表保持锁定
```

#### 2.2.3 海外平台多币种流程

```
1. 进入「汇率维护」录入次月1日的 USD/RUB/GBP 汇率
2. 进入「店铺/平台配置」给海外店铺标记币种（如 OZON-RUB）
3. 上传海外平台账单
4. 系统按"账单期间次月1日"汇率自动换算为 CNY 入账
5. 报表统一用 CNY 展示
```

#### 2.2.4 费用三层分配流程

```
1. 财务进入「数据归集」录入本期费用记录
   （如：推广费 12,500 元 / 运费险 2,800 元）
2. 系统按「分配标准」匹配规则
   （如：推广费按销售收入比例分摊到所有订单商品）
3. 进入「数据分配」查看分配明细
4. 「商品利润表」「利润分析表」自动包含分配费用
```

### 2.3 5 类对账差异桶

| 差异桶 | 触发条件 | 业务含义 |
|---|---|---|
| matched 一致 | 平台销售收入 ≈ 聚水潭资金账单金额 | 完全对齐，无需处理 |
| duplicated 翻倍 | 聚水潭多行 + 金额累计 = 平台 N 倍 (N≥2) | 售后/换货行重复登记 |
| missing_in_jst 聚水潭缺失 | 平台有此单，聚水潭没有 | 未发货 / 导出条件遗漏 |
| missing_in_platform 平台缺失 | 聚水潭有此单，平台账单没有 | 未结算 / 跨月在途 |
| profit_anomaly 利润异常 | \|真实利润 − 系统毛利\| > 阈值 | 成本错登 / 退款漏冲 |

### 2.4 11 平台覆盖

**国内（7）**：抖音、淘宝/天猫、快手、拼多多、小红书、视频号小店、微信小店

**海外（4）**：俄罗斯 OZON (RUB)、俄罗斯 Wildberries (RUB)、英国 TikTok Shop (GBP)、美国 Amazon (USD)

每个平台一个独立适配器文件，通过 `COLUMN_MAP` 把平台列名映射到统一标准列。新增平台只需添加一个映射配置文件，无需改对账引擎。

## 第三章 技术方案与系统架构

### 3.1 技术选型

| 层级 | 选型 | 理由 |
|---|---|---|
| UI 框架 | React 19 | 主流稳定，团队已掌握 |
| 构建工具 | Vite 8 | 冷启动 200ms，HMR 毫秒级 |
| Excel 解析 | SheetJS (xlsx) | 浏览器端零后端解析 .xlsx |
| 样式方案 | CSS Modules + 设计变量 | 轻量，无运行时开销 |
| 图标库 | lucide-react | Tree-shake 友好，包小 |
| 测试 | vitest | 与 Vite 无缝集成 |

### 3.2 数据流

```
原始 Excel
    │
    ├─ 平台资金账单 ──→ 平台 Adapter ──→ 标准 PlatformOrder[]
    │                                          │
    ├─ 聚水潭导出 ────→ parseJushuitan ──→ JstOrder[]
    │                                          │
    ├─ 商品成本表 ────→ findCost              │
    │                                          ↓
    └─ 费用记录 ──────→ runAllocation ──→ Allocation[]
                                              │
                                              ↓
                                    runReconcile（核心对账引擎）
                                              │
                                              ↓
                            ┌─────────────────┴─────────────────┐
                            ↓                                   ↓
                    KPI / 差异行 / SKU 利润           生成 7 张报表
```

### 3.3 模块化结构

```
src/
  App.jsx                      路由壳 + Hook 注入
  components/
    common/                    公共组件（PageHeader/EmptyState/SeedDataBanner）
    settings/                  设置面板组件
    Sidebar / TopBar / ...     主框架组件
  core/
    menuStructure.js           菜单单一来源
    reconcile.js               对账引擎
    allocate.js                三层分配引擎
    reportBuilder.js           7 张报表生成器
    currency.js                汇率引擎（按月取次月1日）
    demoData.js                全局演示数据
  hooks/
    useReconcileStore.js       对账主 Store
    useProductMaster.js        商品资料 + 种子数据
    useProductCost.js          商品成本 + 种子数据
    useCostHistory.js          成本审计日志
    useFeeRecords.js           费用记录
    useAllocStandards.js       分配标准
    useExchangeRates.js        汇率
    useShopProfiles.js         店铺档案
  pages/
    fx/                        汇率管理
    product/                   商品管理（资料/成本/历史）
    shop/                      店铺管理
    system/                    系统设置
    （其他报表页直接放 src/pages 根）
  platforms/
    _shared.js                 平台适配器共享逻辑
    douyin.js / taobao.js /... 11 个平台各自适配器
```

每个文件控制在 200 行内，单一职责，方便维护和扩展。

### 3.4 性能与可扩展性

**性能保障**：
- 报表渲染 500 行虚拟阈值，超过自动截断
- 所有衍生数据用 `useMemo` 缓存
- Hook 状态变更全部 `useCallback` 包裹

**扩展点**：
- 新增平台 → 加一个 `src/platforms/{name}.js`
- 新增报表 → 在 `reportBuilder.js` 加一个 builder 函数
- 新增费用类型 → 在 `useFeeRecords.js` FEE_TYPES 数组追加
- 新增币种 → 在 `currency.js` CURRENCIES 数组追加

### 3.5 数据安全与备份

- 所有数据存浏览器 localStorage，不上传任何外部服务器
- 系统设置 → 数据备份 提供一键导出全部数据为 JSON
- 生产部署可对接后端 API，把 Hook 的持久化层从 localStorage 切到 RESTful 接口

## 第四章 实施计划与里程碑

### 4.1 总体周期

**20 个工作日（4 周自然时间）**，分 4 个阶段交付。

| 阶段 | 工作日 | 自然周 | 主要产出 |
|---|---|---|---|
| 第一阶段 需求确认与原型搭建 | 4 天 | 第 1 周 | 需求确认书 + UI 原型 |
| 第二阶段 核心引擎与商品/成本模块 | 6 天 | 第 2 周 | 对账引擎 + 商品管理三页 |
| 第三阶段 报表与汇率/分配引擎 | 6 天 | 第 3 周 | 7 张报表 + 汇率/分配引擎 |
| 第四阶段 海外平台/系统设置/联调验收 | 4 天 | 第 4 周 | 4 个海外平台 + 系统设置 + 验收 |

### 4.2 详细里程碑

**M1（Day 4 周五）**：原型评审通过，需求清单签字确认

**M2（Day 10 周五）**：对账主流程跑通，能完成抖音 + 聚水潭对账

**M3（Day 16 周五）**：7 张报表全部上线，多币种对账可演示

**M4（Day 20 周五）**：全功能交付，部署上线，培训完成

### 4.3 风险控制

| 风险 | 应对 |
|---|---|
| 客户账单格式与样例不一致 | 第 1 周收集 3-5 个真实账单样本，提前调试适配器 |
| 海外平台账单字段未知 | 预留可视化字段映射工具，让客户自己映射 |
| localStorage 容量超限 | 单店铺月数据 1MB 内，5MB 配额足够；超过给提示 |
| 对账规则边界情况 | 第 3 周末跑 1 个月真实数据回归测试 |

## 第五章 交付内容与验收标准

### 5.1 交付清单

| 类别 | 内容 |
|---|---|
| 源代码 | Git 仓库，含完整提交历史 |
| 部署包 | dist 静态资源 + 部署文档 |
| 文档 | 用户操作手册 + 开发者扩展指南 |
| 数据 | 6 平台演示数据 + 默认配置 |
| 培训 | 1 次现场培训 + 录屏视频 |

### 5.2 验收标准

**功能验收**（19 个菜单页）：
- 每个页面能正常进入，无 console error
- 所有 CRUD 操作可保存到 localStorage 并正确回显
- 7 张报表表头逐字与客户《系统初稿模板》一致
- 4 张账单/利润表的演示数据与客户提供的 Excel 示例一致

**对账准确性**（用客户真实抖音账单回归）：
- 总订单数 ±0.5% 误差内
- matched/duplicated/missing/anomaly 4 桶分类与人工审核一致率 ≥ 95%

**性能验收**：
- 5 万行账单解析时间 < 3 秒
- 切换菜单页响应 < 200ms
- 单元测试 64 个全部通过

**多币种验收**：
- 上传 OZON 卢布账单，能正确按月汇率换算到 CNY
- 跨币种在「店铺利润表」「商品利润表」统一展示为 CNY
